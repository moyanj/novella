# 标准库声明文件方案

日期：2026-11-21。

状态：方案落盘，待确认实施；本文不表示相关机制已经实现。

## 1. 目标与范围

引入类似 TypeScript `.d.ts` 的 `.d.nov` 声明文件，让标准库可以仅描述类型、函数和成员签名，供语义检查与 LSP 使用，运行时实现单独提供。

本轮拟实现声明机制和现有标准库公开接口的声明化，不包含标准库运行时实现、预编译产物发布或完整 ABI 设计。缺少运行时实现的实际使用必须明确报错，不能通过空函数体、占位实现或静默跳过来放行。

本文是待实施方案，不替代当前源码契约。当前标准库状态见 [std/README.md](../std/README.md)，语义覆盖状态见 [sema-coverage.md](sema-coverage.md)。

## 2. 文件形式与使用方式

标准库声明文件采用以下形式：

```text
std/
├── site.d.nov
└── string.d.nov
```

用户保持现有逻辑模块导入方式：

```novella
from "std:string" import String;

func main() -> int {
    let text: String = "hello";
    return text.length() as int;
}
```

上述示例用于说明静态检查，不表示缺少运行时实现时可以原生执行。

`string.d.nov` 的公开接口示例：

```novella
pub class String {
    pub func __init(self);
    pub func __destroy(self);

    pub func length(self) -> usize;
    pub func byteLength(self) -> usize;
    pub func codeUnitAt(self, index: usize) -> u16;
    pub func charCount(self) -> usize;
    pub func equals(self, other: String) -> boolean;
    pub func compare(self, other: String) -> i32;
    pub func concat(self, other: String) -> String;
    pub func slice(self, start: usize, length: usize) -> String;
}
```

保留现有标准库 API，不扩展模块和接口。默认环境继续提供 `String` 与 `string` 别名，用户本地声明优先级沿用当前规则。

不增加 `declare` 关键字，由文件后缀表达整个模块的声明属性。

## 3. 声明文件语义

声明文件参与完整的名称解析、类型注册、签名检查和导入绑定；只是不提供可执行实现。

| 项目 | `.d.nov` 规则 |
| --- | --- |
| 导入、可见性、类型别名 | 沿用现有模块规则（`pub` 重导入可用，见 design §4.3.1.1），不额外引入别名导出能力 |
| 函数、方法 | 只允许签名，以 `;` 结束，禁止函数体 |
| 参数、字段、模块变量 | 必须有显式类型；实例方法的 `self` 沿用属主类型推导 |
| 返回类型 | 无函数体声明省略时为 `void`；普通有体函数和方法省略时由 sema 推导 |
| 泛型与约束 | 正常解析和检查 |
| 字段与模块变量初始化 | 禁止，避免引入模块执行逻辑 |
| 参数默认值 | 允许，复用现有默认实参检查与定义环境展开 |
| 顶层可执行语句 | 禁止 |
| 类型错误、未知类型、重复声明 | 正常报错 |
| `extern` | 保留现有 FFI 含义、限制及 `unsafe` 要求 |

允许参数默认值是对“禁止初始化”的明确例外。默认实参保留在声明 AST 中，按现有规则在调用方展开；其中产生的运行时依赖也必须经过实现可用性检查。

声明函数不能一律转换成 `extern`。实现位于别处不等于使用 C FFI，普通标准库调用也不能因此要求调用方写 `unsafe`。

普通 `.nov` 的语义保持不变，尤其是无函数体方法的抽象含义。对现有 parser 尚不支持的声明形态，应补齐对应语法及文法描述；不能假设可选 AST 字段意味着语法已经支持。

模块变量只表达有类型的外部存储声明，不分配存储、不执行初始化；可变性沿用声明修饰规则。其实际读取、写入或取址需要后续实现绑定。

## 4. 声明方法与抽象方法

当前 `crates/novella-sema/src/check/type_defs/registration.rs` 使用 `method.block.is_none()` 判断抽象方法。引入声明文件后需要区分：

- 普通 `.nov` 中的无体方法：按现有规则属于抽象方法。
- `.d.nov` 中的无体 class 方法：声明外部存在的具体方法。
- trait 方法：仍表达需要实现的接口契约。

不能继续单独根据 `block == None` 判断抽象性。应结合模块种类，集中计算方法的语义身份，让实例化检查、继承检查与后端使用同一个结果。

首期不新增“声明抽象 class 方法”的语法；如需同时描述外部抽象类，应另行定义明确语法，不能根据无体方法猜测。

`FunctionItem` 已有可选函数体，可复用主体 AST。主要补充模块身份与声明合法性检查，不复制一套声明 AST。

## 5. 模块解析与类型身份

给内部模块及对外分析产物增加明确种类，拟采用：

```rust
pub enum ModuleKind {
    Source,
    Declaration,
}
```

加载时识别 `.d.nov`，后续由模块属性驱动检查，避免各阶段重复判断文件名。枚举公开范围根据实际跨 crate 消费方确定。

逻辑模块解析统一检查对应的 `.nov` 和 `.d.nov`：

1. 只有 `.nov`：加载源码模块。
2. 只有 `.d.nov`：加载声明模块。
3. 两者同时存在：报冲突，要求明确选择，避免检查签名和实际实现不一致。
4. 都不存在：保留现有缺少模块诊断。

声明与实现的配对校验不在首期引入，同一路径暂不支持同时放置两份文件。

当前路径解析位于 `crates/novella-sema/src/module/resolve_path.rs`。候选文件选择需要收敛到共享入口，确保模块加载与导入绑定选择同一个文件，并通过现有文件加载抽象兼容 LSP overlay，不能直接依赖磁盘存在性判断。

`String` 继续保留模块与声明位置构成的名义类型身份。字符串字面量、默认环境和显式导入必须引用同一个标准库类型，不能额外合成一份内建 `String`。

入口 `@no_std;` 继续关闭默认环境注入，并按 `std/modules.toml` 的分层限制标准库导入，不因新增声明文件而改变。

## 6. HIR 与原生编译边界

声明文件不产生函数实现、全局初始化或模块初始化代码，其类型和符号身份仍供下游引用。

| 使用场景 | 拟定行为 |
| --- | --- |
| `check`、LSP | 使用完整声明进行类型检查、补全与跳转 |
| 导入声明，但没有运行时使用 | 不因缺少实现而阻止原生编译 |
| 类型别名等可静态消解的使用 | 正常处理 |
| 调用声明函数、读取或写入声明全局变量、取函数或变量地址 | 没有实现绑定则明确报错 |
| 声明 class 的构造、字段访问、析构调用、字符串字面量发射等 | 缺少布局或运行时支持则明确报错 |

不能只跳过声明模块的 HIR 构建，否则调用方仍可能留下无法解释的符号引用。应在调用方降级或其他实际需要实现、布局的边界，使用声明身份给出定位明确的诊断。

只有公开成员签名的 class 不足以确定对象布局。首期允许静态检查，但不能根据声明猜测布局、分配对象或生成析构调用。struct 按值使用同样需要完整布局，不能因为声明了部分字段就假定可安全发射。

实际使用的判据以当前编译流程中需要降级或发射的代码为准，不额外引入全程序可达性分析或死代码消除。

后续原生支持需要独立设计实现绑定、ABI、布局来源、泛型实例化及运行时产物兼容规则。

## 7. 实施顺序

### 7.1 声明模块基础

- 增加模块种类，贯穿加载、分析产物及相关序列化消费者。
- 统一 `.nov` / `.d.nov` 候选解析和同名冲突诊断。
- 检查 parser 对签名语法的支持，补齐缺失形态并同步 `grammar/*.g4`。

### 7.2 声明语义检查

- 集中检查声明文件允许出现的内容。
- 区分声明方法与抽象方法。
- 保留完整的名称、类型、可见性、泛型、默认实参与继承检查。

### 7.3 工具与后端边界

- LSP 识别 `.d.nov`，定义跳转定位到声明文件。
- VS Code 文件识别、文件监听与解析缓存兼容声明后缀。
- 编译缓存纳入文件种类与声明内容，模块候选变化能够使缓存失效。
- HIR 对缺少实现或布局的实际使用明确报错。

### 7.4 标准库迁移与文档

- 将现有标准库公开接口迁入声明文件。
- 更新 `std/README.md`、`docs/design.md`、`docs/stdlib-design.md` 和 `docs/sema-coverage.md`，清理与新机制冲突的描述。
- 旧实现文件的移除在实际操作前单独确认，不能让同名源码和声明文件长期并存。
- 对外导入路径不变；分析产物新增模块种类属于接口变更，相关消费者同步更新。内部源码定位由 `.nov` 迁移为 `.d.nov`。

## 8. 验收标准

- 正确使用 `String` 通过静态检查；错误参数、未知成员、不可见成员仍报错。
- 声明 class 不会仅因方法无体而被判为抽象类，普通源码原有抽象方法规则保持有效。
- 声明文件中的函数体、字段或模块变量初始化、顶层执行语句被拒绝。
- 声明形参和字段缺少必要类型标注时给出明确诊断。
- 默认实参保留定义环境，产生的运行时依赖不能绕过后端检查。
- 默认环境、显式导入、循环导入和 `@no_std` 行为一致。
- 同名 `.nov` / `.d.nov` 冲突被明确报告，包括 LSP overlay 场景。
- LSP 能跳转到 `.d.nov`，修改声明或模块候选能使缓存失效。
- 仅导入声明且无运行时使用的程序不因声明缺少实现而失败。
- 原生编译遇到缺少实现或布局的实际使用时，在编译阶段给出定位明确的诊断。

按仓库约定，默认不新增测试文件；实施时执行适当的现有检查与最小验证用例，记录静态检查通过和原生可执行之间的区别。
